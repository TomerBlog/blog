Exploiting Group Policy Logging and Tracing: Privilege Escalation via Arbitrary File Write

February 29, 2024 · Tomer Nahum

A while ago my colleague Andrea Pierini published his amazing research Do not trust this Group Policy! , Thanks to his research where he demonstrated how to abuse shares to bypass Redirection Guard, he opened the door to many upcoming EOP vulnerabilities. Besides those that were published in his blog, this one is an additional one, following a “hint” by my colleague (Thanks Andrea 😉 )

A standard domain user can exploit Arbitary file write/overwrite via NT AUTHORITY\SYSTEM privileges if a GPO has the “Group Policy Logging And Tracing” option enabled.

The Group Policy Logging And Tracing

This group policy preference allows for the creation of verbose debug logging for many different client side extensions.

This policy can be found Under Computer Configuration -> Administrative Templates -> System -> Group Policy -> Logging and tracing.

Each preference client side extension has multiple options to choose from

  • You can decide what type of data you want to be written to the event logs such as Informational, Errors, Warnings or None.
  • Turning the tracing on and off

And the most important part of this preference options is the ability to specify the tracing location and the maximum size of the trace file.

Why is this part important for us? You might ask yourself.

This is the part where we will be taking advantage off, The location of the log files in the “Group Policy Logging and Tracing” feature can be customized by an Administrator and if it points to a user writable directory we can abuse symlinks.

But why will it work?

Because by default when the size of a computer trace log exceeds the defined maximum size it will rename the file to .bak and a new file is created. To trigger the log rotation the size of a user-controlled source file should be bigger than 1024KB.

Since it’s done with SYSTEM privileges here we’ll use symlinks to place any file we want when creating the appropriate symlinks to any System protected location.

What are Symlinks?

James Forshaw has demonstrated that the Object Manager symbolic links can be used to escalate privileges. He therefore created CreateSymLink to create these kind of symlinks.

To create new links, the user needs to have write access to the directory to link to “RPC Control”, i.e. the one containing the logs. Also, the directory has to be empty to create the soft links.

In relation to our group policy preference the location of the log files can be customized and if it points to a user writable directory we can abuse symlinks.

The problem with Redirection Trust

Previously, since we will perform this from a standpoint of a user the newly created junction will receive a Medium Integrity Level mark. Redirection trust specifies that a highly privileged process should not follow these kind of junctions.

So we have problem here, but can it be bypassed?

The answer is Yes! Thanks to the amazing post by Andrea Pierini he demonstrated how to abuse the shares for bypassing Redirection Guard. So essentially using UNC paths bypasses the Redirection Guard.

Proof Of Concept

We’ll start with setting up a Group Policy preference, in this instance with “Protected Process Light” enabled via Registry.

We now can proceed into actually setting up the GPO with the “Group Policy Logging And Tracing” setting.

We will be conducting this privilege escalation from the workstation WS11-1.

So we’ll need to configure Group Policy Logging And Tracing with the custom paths for WS11-1.

As an admin we can configure the policy with custom logs and do anything we want essentially. if the destination folder is a share , redirection guard is bypassed.

We will now select Configure Registry Preference logging and tracing and configure our custom paths. For the sake of this blog we will be using WS11-1 workstation so we will configure it like so ->

User trace - \ws11-1\gpolo\test\User-%username%.log

Computer trace - \ws11-1\gpolo\test\Computer-%computername%.log

Planning trace - \ws11-1\gpolo\test\User-%username%.log

We’ll keep the maximum size of trace file to 1024KB but that’s important to note. By default when the size of a computer trace log exceeds the defined maximum size it will rename the file to .bak and a new file is created. To trigger the log rotation the size of a user-controlled source file should be bigger than 1024KB.

Obviously, we don’t have to configure all of the traces locations because we only require one with the location we are interested in, in this blog we’ll use the Computer Trace path we added.

We have the following scenario:

An administrator has configured a group policy logging which will write the logfiles on a dedicated computer share.

A regular user can access this computer and has write access to the physical path of this share

The steps are now as follows –

  1. As the domain admin, we will create a shared folder named “gpolo” on WS11-1 and inside of it a shared “test” named folder, we have to have a folder inside a shared folder or else we’ll get an error.

So at least folder1\folder2

  1. As the regular user, we will logon on WS11-1 and we will empty the “test” named folder if it already exists.
  2. We will open cmd and run the following –
1

CreateSymlink.exe C:\Users\example\Desktop\gpolo\test\Computer-WS11-1.log C:\Users\example\Desktop\evil.dll

The file size needs to be bigger than 1024KB that configured in the gpo (in here for example it’s evil.dll).

  1. CreateSymLink.exe C:\Users\example\Desktop\gpolo\test\Computer-WS11-1.bak C:\windows\system32\evil.dll
  2. We will then run gpupdate /force

And now we can see that evil.dll is now in our System32 folder. Redirection Guard was bypassed and we successfully achieved an arbitrary file write.

MSRC Response –

“After careful investigation, this case has been assessed as not a vulnerability and does not meet MSRC’s bar for immediate servicing. You reported RedirectionGuard could be bypassed if an administrator used an SMB path to specify the location of group policy log files. Upon review, this was found to not represent a security vulnerability because it required an administrator to perform parts of the exploit.”

So essentially it won’t be fixed because an admin interaction is required.

The SMB path RedirctionGuard bypass, will definitely be used in many upcoming EOP vulnerabilities. But I guess, Time will tell.
